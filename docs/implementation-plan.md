Отличия реализации от плана:

- **Панель — веб-компонент на чистом JS** без сборки и зависимостей вместо Lit + TypeScript: проще ставить и проверять, внутренние элементы `ha-*` не используются.
- **История пробных запросов хранится в памяти** (последние 288 замеров), без файла `activity.db`; после перезапуска HA она начинается заново. Файл появится вместе с накопителем активности (5.3.1).
- **В категории статистики добавлена «Исключены фильтром»**: recorder exclude проверяется первым, поэтому, например, все 65 статистик «нет состояний» вашей базы попадают в исключённые.
- **Чтение идёт через собственное соединение `mode=ro`** stdlib-модулем `sqlite3` — той же библиотекой SQLite, что у recorder (это важно для корректности блокировок файла), а не через сессию recorder.
- **Вердикты «Кандидатов»:** ⚡ энергия → защищено; есть ссылка → используется; сущности нет / отключена / исключена / без состояний и ссылок нет → можно удалить; остановлена / не в реестре / внешняя → проверить; живая без ссылок → нигде не используется. Встроенный поиск HA (`automations_with_entity` и т. п.) не видит сущности внутри шаблонов, поэтому дополнительно разбирается `raw_config` автоматизаций и скриптов. Шаблоны и хелперы в YAML, Node-RED, AppDaemon и внешние системы не видны — это написано в интерфейсе.
- Не проверено на живой системе: работа на HAOS, наличие `dbstat` в сборке SQLite контейнера, реальное время запросов на вашей ВМ.
Основан на разборе реальной базы (`gitignore/home-assistant_v2.db`, 1,11 ГиБ, схема recorder v53), реестров из `.storage` и актуальных исходников `homeassistant/components/recorder` (ветка `dev`).

**Главная цель:** сделать базу компактнее и убрать из неё мусор — безопасно, без риска её испортить. Аналитика («кто больше всех пишет») — средство для этой цели, а не самоцель.

## 0. Исходные условия и решения владельца

**Среда.** Home Assistant OS в виртуальной машине Proxmox; база на обычном NVMe-диске (M.2), не на SD-карте. СУБД — SQLite, файл `/config/home-assistant_v2.db`.

**Настройки recorder (из `configuration.yaml`):**

| Параметр | Значение | Следствие |
|---|---|---|
| `purge_keep_days` | 7 | в `states` ожидается неделя истории |
| `commit_interval` | 30 | recorder открывает SQLite с `synchronous=NORMAL` (штатное поведение при ненулевом интервале) |
| `exclude` | 5 доменов, 28 масок `entity_globs`, ~60 отдельных сущностей, 3 типа событий | исключение действует и на состояния, и на статистику (см. 2.6) |
| `db_url` | закомментирован (был MariaDB) | в закомментированной строке лежит пароль — в этот документ он не переносился; из файла лучше убрать, а пароль сменить |

**Решения:**

1. **Историю хранить всю.** Автоматических политик «старше N лет — удалить» нет. Удаляется только то, что вы выбрали, по конкретным сенсорам.
2. **Бэкапы — локально**, чтобы возвращать данные без долгой процедуры (раздел 7).
3. **Топы двух видов, это разные объекты:** по частоте записи (таблица `states`, глубина `purge_keep_days`) и по объёму долговременной статистики за месяц/год/всё время (раздел 5).
4. **Диагностика самой базы:** нагрузка, скорость операций, рост, целостность (5.4).
5. **Сенсоры в Home Assistant:** самые «болтливые» сущности за последние 24 часа — топ-N с числом записей за час, за сутки и за всё хранимое окно (5.5).
6. **Оформление:** панель в тёмной теме, как ваши дашборды (раздел 9).
7. **Главная цель не меняется:** сделать базу компактнее и очистить её от мусора. Всё остальное — инструменты для этого.

## 1. Короткие выводы

1. **Форма — кастомная интеграция** (`custom_components/database_cleaner`) со своей панелью в боковом меню, а не add-on/app и не просто карточка. Обоснование — в разделе 3.
2. **Основное место занимает долговременная статистика (LTS), а не текущие состояния.** В копии на неё приходится 90 % файла (в `states` лежат всего двое суток); при полной неделе состояний доля LTS — около 73 %. В любом случае одним `purge` базу заметно не уменьшить — основной выигрыш даст чистка статистики (раздел 2).
3. **Минимум 2,2 млн строк LTS (≈ 163 МиБ, 15 % файла) — бесспорный мусор**: статистика сущностей, которых больше нет или которые отключены. Ещё ~2,6 млн строк — диагностические сенсоры (уровень сигнала, LQI и т. п.), которые почти наверняка не нужны на годы назад.
4. **Писать в базу только через поток recorder** — его очередь задач и официальные API (`recorder.purge_entities`, `recorder.purge`, `async_clear_statistics`). Никаких вторых «писателей», никаких больших `DELETE` одной транзакцией. Это и есть лекарство от «слетающей» базы (раздел 6).
5. **Бэкап только базы возможен** на работающем HA: через SQLite Online Backup API или `VACUUM INTO` из отдельного read-only соединения, с проверкой целостности копии. **Вернуть данные «на лету»** можно выборочно (статистику выбранных сенсоров, без остановки HA); полная подмена файла требует короткой остановки Core (раздел 7).
6. Интерфейс автоматически будет в вашей тёмной теме: панель живёт в том же DOM, что и фронтенд HA, и берёт цвета из CSS-переменных темы (раздел 9).

### 2.5. Проблемы статистики, которые HA уже видит

В `repairs.issue_registry` открыты 6 задач `units_changed_*`: три сенсора `*_lqi`, `sensor.ble_cypress_humidity_*`, `sensor.sun_elevation`, `sensor.sun_azimuth`. Интеграция должна показывать их в одном месте вместе со способом исправления.

### 2.6. Сверка с `recorder: exclude`

Маски и списки из вашего конфига применены к 1733 статистикам recorder (`fnmatch`, как в HA):

- под исключение подпадает **169 статистик, 139 676 строк (≈ 10 МиБ)**; запись у всех уже остановлена, ни одна не «просачивается»;
- в `states_meta` нет ни одной исключённой сущности — фильтр работает корректно;
- по правилам: список `entities` — 22 статистики / 41,6 тыс. строк; `sensor.*_hum` — 24 / 38,7 тыс.; `sensor.*_battery_level` — 47 / 33,4 тыс.; `sensor.*_raw` — 4 / 19,8 тыс.; остальное — мелочь.

Вывод: «хвосты» от исключений — небольшая часть мусора. Основной объём — сироты и отключённые сенсоры (2.3). 162 статистики, у которых запись перестала идти без всякого исключения, имеют другие причины (пропал `state_class`, сменилась сущность) — их разбирает детектор L4.

Следствия для интеграции:

- детекторы помечают статистики, уже подпавшие под `exclude`, — их удаление безопасно и не повторится;
- при генерации новых исключений интеграция предупреждает: исключённая сущность перестаёт попадать **и в статистику** — графики энергии и температур по ней прекратятся.

### 2.7. Следствия для проекта

- Раздел «Статистика» важнее раздела «Состояния». Он должен быть первым экраном после обзора.
- Топы по `states` возможны только в пределах `purge_keep_days` (у вас 7 суток). Для месяца и года используется LTS: она показывает объём и возраст статистики, но не частоту обновлений (раздел 5.2). Накопитель активности для длинных периодов — необязательное дополнение (5.3.1).
- Запросы с `GROUP BY` по всей `statistics` занимают 8–12 с даже на настольном ПК. На железе HA будет дольше — нужны кэш, фоновый расчёт и быстрые оценки по индексу (раздел 5.2).

## 3. Форма: интеграция, а не add-on

| Вариант | Что это | Вердикт |
|---|---|---|
| **Кастомная интеграция + панель** | Python внутри процесса HA Core, свой пункт в боковом меню | **Выбираем** |
| App (бывший add-on) | Отдельный Docker-контейнер под Supervisor | Не подходит как основа |
| Lovelace-карточка | Только фронтенд | Не может ни анализировать, ни чистить |
| Внешний скрипт / Jupyter | Отдельный процесс с прямым доступом к файлу | Это нынешний источник проблем |

Примечание по терминам: в текущей документации HA add-on'ы называются **apps** («Apps used to be called add-ons»); старое название осталось в коде и API.

Почему интеграция:

1. **Один писатель.** Интеграция может ставить задачи в очередь потока recorder — того самого, который единственный пишет в базу. Add-on — это второй процесс в другом контейнере, открывающий тот же файл; именно такая схема (Jupyter) у вас уже ломала базу.
2. **Кэши recorder остаются согласованными.** Recorder держит в памяти соответствия `entity_id → metadata_id` и `statistic_id → id`. Если удалить строки мимо него, он продолжит вставлять данные со старыми идентификаторами. Официальные API сбрасывают эти кэши сами.
3. **Доступ к реестрам.** Группировка по устройствам, интеграциям, зонам, признаки «отключена»/«диагностическая» — всё это есть в `entity_registry`/`device_registry` только внутри Core.
4. **Родной интерфейс.** Панель в том же DOM, та же тема, авторизация HA, доступ только администраторам.
5. **Работает на любом типе установки** (HAOS, Container, Core), а apps — только там, где есть Supervisor.
6. **Распространение через HACS** одним репозиторием.

Чего интеграция не может — **подменить файл базы под работающим recorder**. «Восстановление на лету» тем не менее есть в двух формах: выборочный возврат статистики сенсоров через официальный импорт, без остановки HA (7.4), и полная подмена файла через вспомогательный app с простоем в пару минут (7.5).

```
│   ├── statistics.py      # порционное удаление LTS
│   └── repack.py          # VACUUM через recorder
├── backup.py              # бэкап только базы, проверка, хранение, архив отмены
├── restore.py             # выборочное восстановление статистики через импорт
├── websocket_api.py
├── services.yaml / services.py
├── sensor.py              # топ-N «болтливых» и показатели здоровья БД (5.5)
├── diagnostics.py
├── translations/{en,ru}.json
└── frontend/dist/panel.js # собранный бандл (исходники — в /frontend репозитория)
```

Два пути работы с базой, и они принципиально разные:

**Чтение.** Запросы идут через пул исполнителей recorder: `get_instance(hass).async_add_executor_job(fn)`, внутри — `session_scope(session=instance.get_session(), read_only=True)`. Это штатный способ; в режиме WAL читатели не мешают писателю.

**Запись.** Только задачи в очереди recorder. Три уровня, по убыванию предпочтительности:

| Уровень | Механизм | Для чего |
|---|---|---|
| 1 | Сервисы `recorder.purge`, `recorder.purge_entities` | Удаление состояний, VACUUM |
| 1 | `instance.async_clear_statistics(ids, start_time=…, end_time=…, on_done=…)` | Удаление LTS целиком или за диапазон дат |
| 1 | `async_update_statistics_metadata`, `async_change_statistics_unit`, `async_adjust_statistics` | Исправление проблем статистики |
| 2 | Свой подкласс `RecorderTask` + `instance.queue_task()` | Только то, для чего нет API. Не раньше фазы 5, отдельным решением |

Свои соединения на запись, смена `PRAGMA`, правка схемы и индексов — **запрещены** на уровне дизайна.

Поддерживаемые СУБД: в первой версии очистка и бэкап — только SQLite. Для MariaDB/PostgreSQL — позже и сначала только чтение.

Совместимость: при старте сверяем `SCHEMA_VERSION` recorder с проверенным диапазоном (сейчас 53). Если версия новее проверенной — аналитика работает, действия уровня 1 доступны, всё остальное отключается с понятным сообщением.

## 5. Аналитика

### 5.1. Экран «Обзор»

- Размер файла базы и `-wal`, свободное место на диске.
- Размеры по таблицам и индексам — через виртуальную таблицу `dbstat`. Её наличие в сборке SQLite на HAOS нужно проверить (фаза 0); запасной вариант — оценка «строки × средний размер».
- Число строк и диапазон дат по каждой таблице.
- Настройки recorder: `keep_days`, `commit_interval`, `auto_purge`, `auto_repack`, есть ли фильтр — читаются из атрибутов экземпляра `Recorder`.
- Версия схемы, версия SQLite, длина очереди recorder (`instance.backlog`).
- Плашка «можно освободить ≈ N МиБ» по результатам детекторов.

### 5.2. Долговременная статистика — объём, возраст, мусор

Отдельный объект, источник — таблица `statistics`. Группировка: по статистике / устройству / интеграции / единице измерения / категории из 2.3. Периоды (настраиваются): 30 дней, 90 дней, 365 дней, всё время.

Столбцы: строк за период, ≈ размер (строки × 78 байт), доля от всей LTS, прирост в месяц, первая и последняя запись, источник, категория, найденные проблемы, строк в 5-минутной статистике.

**Что LTS показывает и чего не показывает.**

- В LTS каждый сенсор даёт **ровно одну строку в час**, сколько бы раз он ни менялся. Поэтому здесь видно, «сколько места занимает и как быстро растёт», но не «кто болтливее». Частота обновлений — это раздел 5.3.
- У вас топ-25 по числу строк плоский: у каждого живого сенсора по ~33 450 строк (пишутся с января 2023). Различают сенсоры не объём, а **категория** (сирота, отключён, диагностический, мёртвый), возраст последней записи, единица и устройство. Поэтому главный вид — «Кандидаты» (раздел 8), а топ — вторичный, с фильтрами по этим признакам.
- Короткие периоды (час, сутки) для LTS не нужны: данные в ней появляются раз в час.

**Краткосрочная статистика** (`statistics_short_term`, шаг 5 минут) хранится те же `purge_keep_days`. Топ по ней тоже плоский (по строке на 5 минут у каждого сенсора), поэтому отдельного экрана нет — это столбец «пишется ли сенсор в статистику прямо сейчас».

Производительность:

- Точный `COUNT(*) … GROUP BY metadata_id` по 13,5 млн строк занимает 8–12 с (измерено на настольном ПК; на вашей ВМ выйдет иначе). Запускается в фоне, результат кэшируется (6 ч по умолчанию) и обновляется по кнопке.
- Быстрая оценка без полного прохода: для каждого `metadata_id` берём `MIN(start_ts)` и `MAX(start_ts)` поиском по индексу `(metadata_id, start_ts)` — на реальной базе это 0,1 с на все 1739 статистик. Оценка строк = `(max − min) / 3600 + 1`. Экран открывается мгновенно с оценкой, точные числа подгружаются следом.

### 5.3. Состояния и события — топы по частоте записи

Отдельный объект, источник — таблица `states`; глубина истории ограничена `purge_keep_days` (у вас 7 суток).

Окна по умолчанию: **1 час, 24 часа, 7 дней** (список настраивается). Окно «7 дней» ограничено фактическими данными (`MIN(last_updated_ts)`), и интерфейс прямо пишет «данные за N дн.» — в первые дни после очистки оно будет короче. Размер топа — 10 (по умолчанию), 25 / 50 / 100 по выбору.

Группировка: по сущности / устройству / интеграции / домену / зоне.

Для каждой сущности: записей, записей в час, число уникальных значений, доля `unknown`/`unavailable`, объём уникальных атрибутов, попадает ли в LTS.

```sql
SELECT m.entity_id, COUNT(*) AS rows_cnt, COUNT(DISTINCT s.state) AS distinct_states
FROM states s JOIN states_meta m USING (metadata_id)
WHERE s.last_updated_ts > :since
GROUP BY s.metadata_id
ORDER BY rows_cnt DESC
LIMIT :n;
```

Запрос использует индекс `ix_states_last_updated_ts`; топ за 24 часа на базе с 346 тыс. строк выполнился меньше чем за 0,1 с.

Карточка сущности (по клику): почасовая гистограмма записей, распределение значений, размер атрибутов, сведения о её LTS, предлагаемые действия.

События: топ по `event_type` за окно (у вас половина таблицы `events` — `telegram_sent`).

#### 5.3.1. Накопитель активности (необязательно, фаза 5)

Если захочется знать частоту записи за период **дольше** `purge_keep_days` (месяц, год) — раз в час интеграция считает записи по сущностям за прошедший час и сворачивает в суточные счётчики **в собственном файле** `<config>/database_cleaner/activity.db`. К основной базе он отношения не имеет и её целостности не угрожает. Объём — порядка 1 млн строк в год. Выключен по умолчанию; до включения «за весь период» везде означает «за всё окно `states`».

### 5.4. Диагностика самой базы

Вкладка «Диагностика» и часть экрана «Обзор». Всё — только чтение; история замеров хранится 90 дней в `activity.db`.

| Группа | Показатели | Источник |
|---|---|---|
| Размер и рост | файл, `-wal`, свободное место на диске, прирост за сутки, прогноз «до заполнения диска», доля свободных страниц (`freelist_count / page_count`) и оценка выигрыша от VACUUM | файловая система, `PRAGMA` |
| Нагрузка записи | записей `states` в минуту (1 / 5 / 60 мин), событий в минуту, доля топ-10 сущностей в общем потоке | счёт по индексу `last_updated_ts` |
| Состояние recorder | длина очереди (`instance.backlog`), идёт ли запись, число некорректных остановок (`recorder_runs.closed_incorrect`), время последнего чистого завершения | экземпляр recorder, `recorder_runs` |
| Скорость операций | время пробных запросов: точечный по индексу, «топ за 24 ч», `COUNT` за час; замеряются каждые 5 минут, строится график; рост времени втрое от медианы — предупреждение в «Исправлениях» | собственные замеры |
| Задания обслуживания | длительность и итоги наших заданий: бэкап, удаление порциями, VACUUM (до/после размер, строки, время) | журнал заданий |
| Целостность | `PRAGMA quick_check` и `foreign_key_check` по расписанию (по умолчанию раз в неделю, ночью) на отдельном read-only соединении | SQLite |
| Расхождения | сироты в `state_attributes`/`states_meta`, статистика без метаданных, дубликаты | запросы по индексам |

На диске NVMe пробные запросы будут быстрыми; их цель — заметить **изменение** со временем, а не абсолютные значения. Тяжёлые проверки идут с таймаутом и не чаще раза за запуск; перед запуском проверяется `instance.backlog`.

### 5.5. Сенсоры в Home Assistant

Интеграция создаёт устройство «Database Cleaner» с сенсорами. Данные считаются раз в 10 минут (настраивается) в фоновом потоке.

**Топ «болтливых» за последние 24 часа** — N сенсоров-позиций (по умолчанию 5; `…_chatty_1` … `…_chatty_5`). У каждого:

- состояние — число записей за 24 часа;
- атрибуты: `entity_id`, имя, устройство, интеграция, `count_1h` (за последний час), `count_24h`, `count_window` (за всё окно `states`, с `window_start`), `per_hour_24h`, `distinct_states_24h`, `share_of_all_24h` (доля от всех записей, %), `lts_rows`.

То есть для каждого лидера видно: сколько за час, сколько за сутки, сколько за весь период и насколько часто он пишет. Позиции переиначиваются при смене лидера — на дашборде удобно показывать `entity_id` из атрибута.

**Общие показатели:** записей в час (всего) за час и за сутки; размер базы; размер WAL; свободное место; доля LTS; число строк LTS; число кандидатов на очистку; сколько можно освободить; длина очереди recorder; время пробного запроса; время последнего бэкапа; статус последнего задания. Опционально — бинарный сенсор «есть проблемы» (деградация скорости, провал целостности, давний бэкап).

**Не засорять то, что чистим:**

- тяжёлые атрибуты (списки, подробности) исключаются из записи в recorder через `_unrecorded_attributes`;
- `state_class` у сенсоров **не задаётся**, чтобы они не порождали новую долговременную статистику;
- частые пересчёты не пишут состояние, если значение не изменилось;
- если нужна нулевая запись в историю — интеграция покажет готовую строку `sensor.database_cleaner_*` для вашего `recorder: exclude`.

Сенсоры заменяют ваши прежние SQL-сенсоры (`database_size`, `most_recorded_entity` и подобные — они уже исключены из recorder в вашем конфиге).

## 6. Безопасность: почему база «слетала» и как этого не допустить

### 6.1. Вероятные причины порчи при удалении из Jupyter

Точную причину без логов того момента установить нельзя. Наиболее вероятные механизмы, от самого правдоподобного:

1. **Второй процесс-писатель из другого контейнера.** SQLite полагается на файловые блокировки и на общий файл `-shm`. Между контейнерами (разные пространства монтирования) это работает ненадёжно — на sqlite.org это прямо перечислено среди способов повредить базу.
2. **Большой `DELETE` одной транзакцией.** Он надолго держит блокировку записи (recorder в это время получает `database is locked`), раздувает `-wal` до размеров, сравнимых с базой, и может упереться в свободное место на диске.
3. **Удаление мимо кэшей recorder.** После ручного удаления строк из `states_meta`/`statistics_meta` recorder продолжает писать со старыми идентификаторами — получаются нарушения внешних ключей и «висящие» строки.
4. **Нарушение ссылок внутри `states`.** Поле `old_state_id` ссылается на ту же таблицу; HA перед удалением всегда сначала обнуляет эти ссылки, ручной `DELETE` — нет.
5. **Копирование/перемещение файла базы без `-wal` и `-shm`** или при открытых соединениях.

Что при этом делает сам HA: получив от SQLite ошибку повреждения, recorder **переименовывает** базу (и её `-wal`/`-shm`) в `home-assistant_v2.db.corrupt.<дата>` и создаёт новую пустую. Со стороны это выглядит как «база слетела». Старый файл при этом не удаляется — часть данных из него обычно можно спасти.

### 6.2. Правила, заложенные в дизайн

| № | Правило | Как обеспечивается |
|---|---|---|
| R1 | Один писатель | Все изменения — задачи в очереди recorder; своих пишущих соединений нет |
| R2 | Сначала официальные API | Уровень 1 из раздела 4; собственный SQL на запись в версии 1 отсутствует |
| R3 | Маленькие транзакции | Не больше ~50 тыс. строк на транзакцию (настраивается); см. 8.2 |
| R4 | Проверки перед запуском | Раздел 6.3; не пройдены — кнопка неактивна, причина показана |
| R5 | Сначала «сухой прогон» | Любое действие сначала показывает точные числа: что удалится и сколько освободится |
| R6 | Бэкап перед удалением | Требуется проверенный бэкап не старше N часов (по умолчанию 24) либо явный отказ пользователя |
| R7 | VACUUM один раз, в конце | Только штатным путём HA (`recorder.purge` с `repack: true`) |
| R8 | Одно задание одновременно | Глобальная блокировка в менеджере заданий |
| R9 | Пауза и отмена | Отмена срабатывает между порциями; после перезапуска HA задание помечается прерванным, «половинных» транзакций не бывает |
| R10 | Не перегружать recorder | Перед каждой порцией проверяется `instance.backlog`; выше порога — ждём |
| R11 | Журнал | Каждое задание записывается: что, когда, сколько строк, размеры до и после |
| R12 | Подтверждение | Для разрушающих действий — ввод контрольного слова |
| R13 | Можно отменить | Перед удалением статистики выбранных сенсоров их строки выгружаются в архив отмены (7.4); архив хранится 30 дней |

### 6.3. Проверки перед разрушающим действием (preflight)

1. Recorder запущен, HA в состоянии `running`, миграция схемы не идёт (`async_migration_in_progress`).
2. Диалект — SQLite, версия схемы в проверенном диапазоне.
3. Нет другого задания интеграции и не идёт штатный бэкап HA.
4. Очередь recorder ниже порога.
5. Свободного места достаточно: для удаления — запас под рост `-wal`; для VACUUM — **не меньше двух текущих размеров базы** (для вашей базы ≈ 2,3 ГиБ).
6. `PRAGMA quick_check` возвращает `ok`.
7. Есть свежий проверенный бэкап (R6).

## 7. Бэкап только базы данных и восстановление

### 7.1. Где хранится

Локально, на диске виртуальной машины HAOS. По умолчанию `/share/database_cleaner/backups`: каталог `/share` общий для Core и apps (нужно для 7.5), а штатные бэкапы HA лежат отдельно, в `/backup`. Путь проверяется через `hass.config.is_allowed_path`.

Что это даёт: быстрое восстановление без сети. Чего не даёт: тот же диск — защита от ошибок и порчи базы, но не от потери диска. От неё остаются еженедельный штатный бэкап HA на NAS и, если хотите, снимок ВМ в Proxmox перед крупной очисткой (это отдельный, самый грубый и самый надёжный уровень отката целиком).

Место: для вашей базы (≈ 1,1 ГиБ) две копии — ≈ 2,2 ГиБ, плюс запас на VACUUM ≈ 2,3 ГиБ. Перед запуском интерфейс показывает «нужно X, свободно Y» и блокирует действие, если не хватает. Хранится последних N копий (по умолчанию 2).

### 7.2. Способы создания

| Способ | Как работает | Плюсы | Минусы |
|---|---|---|---|
| **A. Online Backup API** (по умолчанию) | Отдельное read-only соединение, `sqlite3.Connection.backup(dst, pages=-1)` в потоке-исполнителе | Быстро, согласованный снимок, recorder продолжает писать | Копия того же размера, что и оригинал |
| **B. `VACUUM INTO 'файл'`** | Читающая транзакция создаёт сразу упакованную копию | Копия компактнее; заодно даёт точный прогноз размера после VACUUM | Дольше, больше нагрузка на CPU |
| C. Блокировка recorder + копирование файла | `instance.lock_database()` → копия → `unlock_database()` — так делает штатный бэкап HA | Проще всего | Запись приостановлена, события копятся в памяти |

A и B — только чтение, правило R1 не нарушают. Способ A запускается одним шагом (`pages=-1`): при пошаговом копировании каждая запись recorder заставляла бы копирование начинаться заново. Пока снимок удерживается, `-wal` не может быть сброшен и немного растёт — на время бэкапа это нормально. Способ C — запасной.

### 7.3. Проверка и манифест

1. `PRAGMA integrity_check` на копии.
2. Сверка числа строк в ключевых таблицах со снимком на момент начала.
3. SHA-256 файла.
4. Рядом пишется `*.json`: дата, версия HA, версия схемы, размер, счётчики строк, хэш, способ, результат проверки.

Бэкап считается пригодным (для R6) только после успешной проверки. Опционально — сжатие gzip после проверки.

### 7.4. Выборочное восстановление «на лету» (основной способ)

Нужно, когда вы удалили лишний сенсор. HA не останавливается, остальные данные не затрагиваются.

- **Источники:** архив отмены последней очистки (строки только удалённых сенсоров, сжатый файл рядом с журналом, хранится 30 дней) или любой полный бэкап — из него можно выбрать конкретные сенсоры.
- **Механизм:** официальный импорт статистики (`async_import_statistics` для статистик-сущностей с источником `recorder`) — запись идёт через очередь recorder, как и любое другое изменение. Метаданные (`unit_of_measurement`, `unit_class`, `mean_type`, `has_sum`) восстанавливаются из архива.
- **Порядок в интерфейсе:** выбрать сенсоры → сухой прогон (сколько строк, какой диапазон, пересекается ли с уже имеющимися данными) → выполнение порциями с прогрессом и отменой.
- **Граница возможностей:** возвращается долговременная статистика. Таблица `states` из бэкапа так не восстанавливается — она живёт неделю и ценности для отката почти не имеет; в интерфейсе это написано явно.
- **Что проверить в фазе 0:** сохраняются ли `sum`, `state`, `last_reset` без искажения; допустим ли импорт для сенсоров, которых уже нет в системе; что происходит при пересечении диапазонов (импорт перезаписывает строки с тем же `start`).

### 7.5. Полное восстановление файла базы — с коротким простоем

Подменить файл под живым recorder нельзя. Поэтому для полного отката предусмотрен вспомогательный app (Supervisor) «Database Cleaner Restore Helper» с доступом к `/config` и `/share`. По команде из панели:

1. Проверка выбранного бэкапа (манифест, `integrity_check`).
2. Остановка Core через Supervisor API.
3. Текущие `home-assistant_v2.db`, `-wal`, `-shm` переименовываются в `*.before-restore.<дата>` (не удаляются).
4. Копирование бэкапа на место базы.
5. Запуск Core.

Простой — порядка 1–3 минут (оценка, замерить в фазе 0). Права app на остановку и запуск Core нужно сверить с документацией Supervisor (фаза 5). Если app не установлен — те же шаги вручную: `ha core stop`, переименование, копирование, `ha core start`; интерфейс показывает эту инструкцию рядом с каждым бэкапом.

Штатный бэкап HA остаётся вторым уровнем защиты и этим проектом не заменяется.

## 8. Очистка и обслуживание

### 8.1. Поиск мусора — детекторы

Каждый детектор выдаёт список объектов, число строк, оценку размера и рекомендуемое действие. Пороги настраиваются. В скобках — что детектор нашёл бы в вашей базе.

**Долговременная статистика**

| Код | Правило | Находка |
|---|---|---|
| L1 | Сирота: `statistic_id` нет в реестре сущностей и нет текущего состояния | 587 шт., 1,50 млн строк |
| L2 | Сущность отключена, статистика осталась | 219 шт., 0,70 млн |
| L3 | Нет новых данных дольше N дней (30 / 365) | 939 / 703 шт. |
| L4 | Сущность активна, но LTS больше не пишется | 162 шт., 0,61 млн |
| L5 | Диагностическая сущность со статистикой | 316 шт., 2,62 млн |
| L6 | «Малоценные» единицы: `dBm`, `lqi`, объёмы дисков | ~1,5 млн строк |
| L7 | Имя похоже на временное: `test`, `tmp`, `debug` | `sensor.input_number_test` |
| L8 | Короткоживущая: всего несколько строк | чужие BLE-датчики по 3–6 строк |
| L9 | Ряд-константа: значение не менялось за всю историю | уточняется при реализации |
| L10 | Проблема, найденная самим HA (раздел 8.4) | 6 открытых `units_changed` |

**Состояния и события**

| Код | Правило | Находка |
|---|---|---|
| S1 | «Болтливая» сущность: больше X записей в час | `sensor.tasmota_pve1_power` — ~680/ч |
| S2 | Много записей при малом числе разных значений | `sensor.zha_switch_olive_power`: 4667 записей, 4 значения |
| S3 | Тяжёлые уникальные атрибуты на каждую запись | `event.ha_debug_update_event` — 708 КиБ |
| S4 | Частые переходы в `unavailable`/`unknown` | `sensor.palaiseau_next_rain` — 486 |
| S5 | Сущности нет в реестре | 287 `entity_id` |
| S6 | Домены/категории, история по которым редко нужна | `update`, `button`, `notify`, диагностические |
| S7 | Доминирующий тип события | `telegram_sent` — 48 % событий |

Сироты (L1) и отключённые (L2) предлагаются к удалению по умолчанию. Всё остальное — только как кандидаты: решение за пользователем, с возможностью пометить «оставить навсегда» (список исключений хранится в настройках интеграции).

### 8.2. Действия

**1. Удалить статистику выбранных сенсоров** (для L1, L2, L7, L8 и по вашему выбору: один сенсор, все сенсоры устройства, произвольный набор). Автоматических политик хранения нет — решение всегда за вами. Перед удалением строки уходят в архив отмены (R13, раздел 7.4).
`instance.async_clear_statistics(statistic_ids, on_done=…)`. Штатная функция удаляет запись из `statistics_meta`; строки в `statistics` и `statistics_short_term`, судя по схеме (`ON DELETE CASCADE`, при соединении включается `PRAGMA foreign_keys=ON`), уходят каскадом — **это нужно подтвердить на тестовой копии в фазе 0**.

Порционность — наша ответственность: штатная функция удаляет все переданные идентификаторы одной транзакцией. Менеджер заданий набирает в порцию столько статистик, чтобы суммарно выходило не больше ~50 тыс. строк (для «полных» статистик по 33 тыс. строк — одна-две за раз), ждёт `on_done`, проверяет очередь recorder, делает паузу и берёт следующую порцию. Для ваших 587 сирот это порядка 30–40 коротких транзакций вместо одной на 1,5 млн строк.

Вызываем метод экземпляра напрямую, а не WS-команду `recorder/clear_statistics`: у той жёсткий тайм-аут 10 секунд.

**2. Обрезать статистику по дате** («оставить последние N лет» для выбранных сенсоров).
Тот же метод с `start_time`/`end_time` — штатная поддержка диапазона. Диапазон режется на отрезки (например, по месяцам), чтобы каждая транзакция оставалась маленькой. Для накопительных статистик (`sum`) удаление старого хвоста безопасно: более поздние значения суммы не меняются.

**3. Удалить состояния сущностей.**
Сервис `recorder.purge_entities` (`entity_id` / `domains` / `entity_globs`, `keep_days`). Он сам работает порциями и перезапускает себя до завершения. Важно: он удаляет только состояния и не трогает статистику.

**4. Перестать записывать впредь.**
Фильтр recorder задаётся только в `configuration.yaml`, интеграция изменить его не может. Поэтому она **генерирует готовый фрагмент YAML** (`recorder: exclude: …`) в том же стиле, что и ваш текущий конфиг (отдельные `entities`, маски `entity_globs`, `domains`), для выбранных сущностей, доменов и шаблонов — с предупреждением, что исключение останавливает и долговременную статистику, а для «болтливых» сенсоров дополнительно подсказывает, где уменьшить частоту у источника (интервал отчёта в Tasmota/ESPHome, параметры отчётов ZHA). Отключение сущности — отдельным действием через реестр.

**5. Сжать базу (repack).**
`recorder.purge` с `repack: true` — выполняет `VACUUM`, после чего HA сам делает контрольную точку WAL и `PRAGMA optimize`. Запускается один раз в конце цикла очистки. Учесть: сервис заодно удалит состояния старше `keep_days` — это то же, что делает ночная очистка. Место на диске реально освобождается только на этом шаге: до него удалённые строки лишь превращаются в свободные страницы внутри файла.

### 8.3. Типовой сценарий «Очистить базу» (мастер)

1. Анализ → список кандидатов с оценкой выигрыша.
2. Пользователь отмечает, что удалять.
3. Сухой прогон: точные числа строк.
4. Preflight (6.3).
5. Бэкап базы и его проверка.
6. Порционное удаление с индикатором прогресса и кнопкой отмены.
7. Repack.
8. Отчёт: размер до и после, что удалено, запись в журнал.

### 8.4. Проблемы долговременной статистики

Интеграция объединяет проверки HA и собственные.

Что находит сам HA (`validate_statistics`, те же данные, что в «Инструменты разработчика → Статистика»):

| Тип | Смысл | Исправление |
|---|---|---|
| `units_changed` | Единица сенсора не совпадает с единицей в метаданных | Сменить единицу в метаданных / пересчитать / удалить |
| `state_class_removed` | У сенсора пропал `state_class` | Вернуть `state_class` или удалить статистику |
| `mean_type_changed` | Изменился тип усреднения | Удалить и начать заново |
| `entity_no_longer_recorded` | Сущность исключена из recorder, статистика осталась | Вернуть в запись или удалить |
| `entity_not_recorded` | Есть `state_class`, но сущность исключена | Информационное |
| `no_state` | Статистика есть, состояния нет | Удалить |

Первые три типа HA также показывает в «Исправлениях» (`<тип>_<statistic_id>`).

Собственные проверки: категории из 2.3; разрывы во времени; скачки и убывание `sum` у накопительных счётчиков; строки без единого значения; расхождение между краткосрочной и долговременной статистикой.

Исправления — только штатными функциями: `async_update_statistics_metadata` (передавать и `unit_class` — вызов без него объявлен устаревшим), `async_change_statistics_unit`, `async_adjust_statistics`, `async_clear_statistics`.

## 9. Интерфейс

**Технология.** Веб-компонент на Lit + TypeScript, сборка в один файл. Регистрация:

- статика — `hass.http.async_register_static_paths([StaticPathConfig(url, path, cache_headers)])`;
- панель — `panel_custom.async_register_panel(hass, frontend_url_path="database-cleaner", webcomponent_name="database-cleaner-panel", module_url=…, sidebar_title=…, sidebar_icon="mdi:database-cog", require_admin=True, embed_iframe=False)`.

**Тёмная тема.** Панель не в iframe, поэтому наследует CSS-переменные активной темы и будет выглядеть как ваши дашборды: тёмные карточки со скруглением, те же шрифты и акцентные цвета. Используются `--primary-text-color`, `--secondary-text-color`, `--card-background-color`, `--primary-color`, `--divider-color`, цвета состояний, плюс новые токены `--ha-*` с запасными значениями. Жёстко заданных цветов нет — светлая тема тоже будет работать.

**Встроенные элементы.** `ha-card` используем (де-факто стабилен). Остальные `ha-*` официально не являются публичным API и могут измениться в любом релизе, поэтому таблицы, кнопки и шапка — свои. Панель сама отвечает за заголовок и кнопку открытия меню на узком экране.

**Графики.** Простые горизонтальные полосы и гистограммы на SVG/CSS, без тяжёлой библиотеки.

## 14. Открытые вопросы

**Технические — закрыть в фазе 0 на тестовом экземпляре:**

1. Подтвердить каскадное удаление строк при `clear_statistics` (тело `statistics_meta_manager.delete` не просмотрено).
2. Доступна ли `dbstat` в сборке SQLite внутри контейнера HA.
3. Точные сигнатуры `lock_database` / `unlock_database` в текущем `core.py` (нужны только для запасного способа бэкапа C).
4. Реальное время `VACUUM`, бэкапа и полного восстановления на вашей ВМ.
5. Корректность импорта статистики при восстановлении: сохраняются ли `sum`/`state`/`last_reset`, допустим ли импорт для сенсоров, которых уже нет (7.4).
6. Права вспомогательного app на остановку и запуск Core через Supervisor API (7.5).
